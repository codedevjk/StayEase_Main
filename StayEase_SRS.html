🏨 StayEase

Hotel Reservation Platform
Capstone Project SRS
Author: Jagmohan Kushwaha

1. Project Overview

StayEase is a modern, full-stack hotel reservation platform designed to streamline the process of discovering, booking, and managing hotel stays across India. It provides an end-to-end digital platform enabling guests to securely register, search hotels by destination, view detailed room availability, simulate online payments, and manage their reservations — from booking through check-in, check-out, and post-stay reviews.

The application strictly enforces role-based workflows for two primary user types:

  • Guests (ROLE_USER): Can register, log in, browse the hotel catalog with search and filters, view hotel details with real-time room availability, book rooms (PREPAID with 10-minute inventory hold or PAY_LATER), manage their reservations (view, cancel, check-in, check-out, download invoice), and submit one review per completed stay.
  • Administrators (ROLE_ADMIN): Can log in to the admin portal and manage hotel properties (CRUD), room types, physical rooms and housekeeping status, pricing/rate overrides, all reservations (admin-initiated check-in, check-out, cancellation, no-show, refund), review moderation (approve/reject), and view audit trails for all system events.

The project is built as a microservices-based architecture using Java 21, Spring Boot 3.3.5, Spring Cloud (Gateway + Consul), Spring Security with JWT, and Angular 16 — demonstrating modern enterprise development practices at a capstone-level of complexity.

2. System Architecture

The solution follows a Microservices Architecture consisting of four business services: User Service, Property Service, Reservation Service, and Review Service, with communication managed through Spring Cloud Gateway and Spring Cloud Consul. All frontend requests must pass through the API Gateway. Inter-service communication uses WebClient (reactive) with Resilience4j circuit breakers.

2.2 Authentication & Authorization Design

Important: StayEase uses a JWT-Based Stateless Security Design. On successful login, the User Service issues a signed JWT (JJWT library). The token is stored in browser localStorage and cleared on logout. Every downstream microservice runs its own JwtAuthenticationFilter (Spring Security) to validate the Bearer token, extract the UserPrincipal (user ID, email, role, token version), and establish the security context. Furthermore, downstream services verify the tokenVersion claim with the User Service (fail-closed check via UserServiceClient) so that existing JWTs are immediately rejected if a password reset or email update has occurred. The API Gateway manages ingress routing, attaches a unique X-Correlation-ID to every request and response, and passes the Bearer token downstream. Internal inter-service endpoints (/internal/**) are protected and called only via WebClient from trusted services.

3. Getting Started

3.1 Setup Steps

  1. Start Consul for service discovery: consul agent -dev
  2. Ensure MySQL 8+ is running on port 3306.
  3. Initialize the databases by running each SQL DDL script from src/main/resources of each microservice:
    mysql -u root -p < backend/user-service/src/main/resources/user_db.sql
    mysql -u root -p < backend/property-service/src/main/resources/property_db.sql
    mysql -u root -p < backend/reservation-service/src/main/resources/reservation_db.sql
    mysql -u root -p < backend/review-service/src/main/resources/review_db.sql
  4. Start each backend microservice in separate terminals:
    cd backend/api-gateway && mvn spring-boot:run
    cd backend/user-service && mvn spring-boot:run
    cd backend/property-service && mvn spring-boot:run
    cd backend/reservation-service && mvn spring-boot:run
    cd backend/review-service && mvn spring-boot:run
  5. Bootstrap the admin account (one-time): add stayease.admin-bootstrap.enabled=true and stayease.admin-bootstrap.admin-password=Admin@1234 to user-service config, restart the User Service. The generated admin email defaults to admin@stayease.local. Disable the flag immediately after the first run.
  6. Start the Angular application: run npm install then ng serve from frontend/stayease-ui/.
  7. Open http://localhost:4200 and log in with the bootstrapped admin credentials to seed hotel and room data via the Admin Portal.

4. User Stories

The following fifteen user stories define the complete functional scope of the StayEase platform and have been fully implemented in this repository.

US 01 — User Registration

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As an anonymous visitor, I want to securely register so that I can access the StayEase platform and book hotel stays.
  • Customers shall be able to register using their Full Name, Email Address, Phone Number, and Password.
  • Email addresses must be unique across the platform; duplicate registrations shall not be allowed, and the system must return a clear validation error.
  • Passwords must be securely hashed and encrypted before storage; plaintext passwords shall never be saved or logged.
  • Newly registered accounts shall automatically be assigned a standard customer role; administrator privileges cannot be self-assigned.
  • Mandatory fields must be validated before registration, including valid email formatting, non-empty phone number, and minimum password length.
  • Clear and descriptive validation error messages must appear immediately below invalid fields if inputs are invalid or missing.
  • Upon successful registration, the system shall display a success confirmation and smoothly redirect the user to the login page.

US 02 — User Login & Logout

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As a registered user, I want to log in so that I can access features suited to my assigned role.
  • Users shall authenticate using their registered Email Address and Password.
  • Upon successful authentication, the system issues a secure authorization token that maintains the user's active session.
  • Session information is securely preserved across page refreshes and cleared immediately upon logout.
  • Upon successful login, standard customers are directed to the hotel search page, while administrators are redirected to the management dashboard.
  • Users shall be able to log out securely at any time, which immediately terminates their active session and returns them to the home page.
  • The system enforces active session validation across all services, ensuring revoked or outdated sessions are immediately denied access.
  • Mandatory fields must be validated before submission, and clear error messages shall be displayed for failed attempts.

US 03 — View & Update Profile

Priority: Must Have Primary Microservice: User Service

Acceptance Criteria

  • As an authenticated guest, I want to view and manage my profile details so that my account information remains accurate.
  • The system shall display the guest's Full Name, Email Address, Phone Number, and Address.
  • Guests can update their personal information including Full Name, Phone Number, and Address.
  • Guests can update their Email Address by verifying their current password for enhanced account security.
  • Updating an email address invalidates previous login sessions across all devices, requiring a fresh login with the new credentials.
  • Administrators can perform password resets for user accounts when required, which also terminates existing sessions for that user.
  • Profile management operations securely deduce identity from the active login session, strictly preventing unauthorized modifications across accounts.
  • Clear validation and success messages shall be displayed for all profile updates.

US 04 — Admin Hotel Property Management

Priority: Must Have Primary Microservice: Property Service

Acceptance Criteria

  • As an administrator, I want to manage hotel properties so that the platform catalog remains accurate and comprehensive.
  • Administrators can view a structured and paginated list of all hotel properties, showing Property Name, Destination, Star Rating, and Active Status.
  • Hotel property names shall be displayed cleanly without technical clutter, duplicate prefixes, or trailing empty formatting characters.
  • Administrators can add new hotel properties by providing Name, Destination, Address, Contact Email, Contact Phone, Description, Star Rating (one to five stars), Image URL, and selectable Amenities.
  • Administrators can edit all metadata and contact details of an existing hotel property.
  • Administrators can toggle a hotel's status between Active and Inactive.
  • Only properties marked as Active are visible in the public search catalog; Inactive properties are hidden from customer view and cannot be booked.
  • All hotel creation, update, and status change actions are permanently recorded in an administrative audit trail.

US 05 — Admin Room Type Management

Priority: Must Have Primary Microservice: Property Service

Acceptance Criteria

  • As an administrator, I want to manage room types for each hotel so that customers can choose from distinct accommodation options.
  • Administrators can create room types under a hotel, specifying Name, Description, Maximum Guest Capacity, Base Nightly Rate in Indian Rupees, and Image URL.
  • Administrators can modify room type details and adjust standard nightly rates.
  • Administrators can define date-specific pricing overrides on any room type to accommodate seasonal variations, holidays, and high-demand periods.
  • The system automatically prioritizes active date-specific rates over standard base rates when calculating stay totals for requested date ranges.
  • Deleting or retiring room types must maintain historical integrity for existing bookings.

US 06 — Admin Physical Room & Housekeeping Management

Priority: Must Have Primary Microservice: Property Service

Acceptance Criteria

  • As an administrator, I want to manage physical rooms and housekeeping statuses so that inventory accurately reflects operational readiness.
  • Physical rooms track both a Cleanliness Status (Clean, Dirty, or Inspecting) and an Operational Status (Operational or Out of Service).
  • Administrators can add physical rooms by specifying Room Number, Floor, Room Type, and initial cleanliness status.
  • Administrators can update room cleanliness status as rooms are serviced, inspected, and made ready for arriving guests.
  • Administrators can mark individual physical rooms as Out of Service for maintenance, temporarily excluding them from sellable inventory.
  • Only rooms marked as Operational contribute to the hotel's bookable capacity for that room type.
  • Upon booking confirmation, the system automatically assigns an available physical room to the reservation.

US 07 — Browse & Search Hotels

Priority: Must Have Primary Microservice: Property Service

Acceptance Criteria

  • As a guest, I want to search and filter available hotels using destination, dates, and party size so that I can find suitable accommodations.
  • The homepage provides an intuitive horizontal search interface with quick-select shortcuts for popular trending travel destinations.
  • Customers can search by specifying Destination, Check-In Date, Check-Out Date, Number of Rooms, Adults count, and Children count.
  • Validation Rules:
    1. Check-in date cannot be in the past.
    2. Check-out date must be strictly after the check-in date.
    3. At least one adult is required to make a booking; reservations for unaccompanied children are strictly disallowed.
  • If search inputs violate validation rules, helpful error messages appear immediately beneath the fields, and navigation is paused until corrected.
  • The system automatically calculates room requirements based on standard hotel occupancy norms of two adults per room, accommodating children alongside adults.
  • Search results display only active hotels matching the criteria, showing property name, destination, star rating, verified guest review score, starting price per night, and thumbnail photography.
  • Results can be filtered by star rating and price range, with clean pagination for ease of browsing.

US 08 — View Hotel Detail & Room Availability

Priority: Must Have Primary Microservice: Property Service + Reservation Service

Acceptance Criteria

  • As a guest, I want to view detailed property information and real-time room availability for my selected dates so that I can choose a room.
  • The hotel detail page showcases property name, destination, address, star rating, verified guest ratings, amenity badges, and high-resolution photos.
  • The system checks real-time room availability across the selected date range and presents distinct visual states for each room type:
    1. Sold Out / Zero Rooms Available: The room card is visually subdued and clearly labeled as Sold Out or Unavailable for selected dates, with the reservation button disabled.
    2. Low Inventory: When only one to three rooms remain, an urgent indicator highlights the limited availability.
    3. Normal Availability: Displays the exact count of available rooms ready for booking.
  • Pricing information clearly outlines the nightly rate and the estimated total cost for the stay, including applicable taxes.
  • Verified guest reviews submitted by past travelers are displayed in a dedicated reviews section below the room types.
  • Unauthenticated visitors attempting to book a room are prompted to log in or register, returning seamlessly to their booking upon sign-in.

US 09 — Make a Hotel Reservation

Priority: Must Have Primary Microservice: Reservation Service

Acceptance Criteria

  • As an authenticated guest, I want to book a room so that I can secure accommodations for my stay.
  • The booking flow guides the customer through a step-by-step confirmation: reviewing stay details, selecting a payment policy, and viewing confirmation.
  • The system presents a transparent, itemized cost summary showing the lodging subtotal, mandatory taxes, and grand total.
  • Customers choose between two flexible payment policies:
    1. Prepaid: The guest completes online payment during booking, which reserves the room under a temporary ten-minute inventory hold while payment is processed.
    2. Pay at Property: The booking is confirmed immediately without upfront payment, with payment collected upon arrival at the property.
  • Inventory is verified across every night of the stay to prevent overbooking, even during peak concurrent traffic.
  • Upon successful confirmation, the system generates a unique, human-friendly booking reference number (e.g., SE-2026-9826).
  • An operational physical room is automatically assigned to the reservation, and an immutable audit event is logged.

US 10 — Payment Processing (Simulated)

Priority: Must Have Primary Microservice: Reservation Service

Acceptance Criteria

  • As a customer choosing a prepaid reservation, I want to complete payment through a simulated checkout so that my booking is officially confirmed.
  • The checkout interface displays the booking reference number, total amount due, and three simulated payment options:
    1. UPI: Accepts a valid Virtual Payment Address, validating the standard payment handle format.
    2. Credit or Debit Card: Accepts a sixteen-digit card number, cardholder name, valid future expiration date, and security code, validating each field individually.
    3. Net Banking: Enables selecting from major banking institutions.
  • The simulation provides options to demonstrate both successful and unsuccessful payment transactions for testing and verification purposes.
  • Upon a successful transaction:
    • The reservation is confirmed, the inventory hold is converted to an active booking, payment status is marked as paid, and a printable invoice is generated.
  • Upon a failed transaction:
    • The reservation is marked as payment failed, the temporary inventory hold is immediately released back to available inventory, and the customer is given the option to retry.
  • If a prepaid booking remains unpaid past the ten-minute window, a background process automatically cancels the expired hold and returns the room to available inventory.

US 11 — My Reservations

Priority: Must Have Primary Microservice: Reservation Service

Acceptance Criteria

  • As a guest, I want to view and manage all my past and upcoming reservations so that I have complete control over my travel plans.
  • The system provides a centralized dashboard showing all bookings associated with the customer's account, arranged chronologically with the newest first.
  • Each reservation card displays the booking reference number, hotel name, room type, travel dates, duration of stay, guest count, total cost, payment policy, and current status.
  • Bookings progress through distinct operational statuses: Pending Payment, Confirmed, Checked In, Checked Out, Cancelled, No-Show, or Payment Failed.
  • Customers can view and download an itemized tax invoice for any confirmed or completed reservation.
  • Customers can cancel confirmed bookings before the check-in date by providing a cancellation reason, which immediately returns the reserved room to open inventory.
  • Once a stay is completed and checked out, the customer is presented with an option to write a review, provided they have not already submitted one for that booking.

US 12 — Self Check-In & Check-Out

Priority: Must Have Primary Microservice: Reservation Service

Acceptance Criteria

  • As a guest, I want to perform self check-in and check-out so that I can streamline my arrival and departure without waiting in line.
  • Guests can initiate self check-in for confirmed reservations on or after the scheduled check-in date, updating their booking status to Checked In.
  • Guests can initiate self check-out at the conclusion of their stay, updating their booking status to Checked Out and recording the departure timestamp.
  • Completing check-out automatically alerts property housekeeping by updating the physical room status to Dirty, scheduling it for turnover and sanitization.
  • Successful check-out unlocks the guest's eligibility to rate and review their stay.
  • Customers can only check-in and check-out of their own reservations; unauthorized attempts are strictly rejected.

US 13 — Submit & View Reviews

Priority: Must Have Primary Microservice: Review Service

Acceptance Criteria

  • As a customer who has completed a stay, I want to share my feedback and ratings so that other travelers can make informed decisions.
  • Reviews can only be submitted for completed reservations with a Checked Out status; pending, active, or cancelled stays cannot be reviewed.
  • The system strictly permits only one review per booking per customer; once a review is submitted, duplicate attempts are rejected across all layers of the application.
  • A review consists of a numerical star rating from one to five stars and written commentary describing the guest's experience.
  • Newly submitted reviews by verified guests are published to the platform, and the hotel's overall average rating and review count are updated automatically.
  • Administrators can review customer feedback and remove inappropriate content by recording a documented moderation reason, which withdraws the review from public display.
  • Hotel listings display only active, published reviews from verified guests.

US 14 — Admin Reservation Management

Priority: Must Have Primary Microservice: Reservation Service

Acceptance Criteria

  • As an administrator, I want to view and manage all platform reservations so that I can maintain operational control and assist guests.
  • Administrators can view a comprehensive master table of all reservations across all hotels, with search and filtering capabilities.
  • Administrators can perform administrative actions on any booking, including processing check-ins, check-outs, cancellations, and payment reconciliations.
  • Administrators can record guest No-Shows when customers fail to arrive, which safely frees the reserved room back into sellable inventory without issuing an unwarranted refund.
  • Every administrative action is permanently logged in the reservation audit trail with the administrator's identity and timestamp.

US 15 — Admin Dashboard & Audit Trails

Priority: Must Have Primary Microservice: All Services

Acceptance Criteria

  • As an administrator, I want to monitor operational metrics and inspect system audit trails so that I can track business performance and ensure accountability.
  • The management dashboard displays real-time operational statistics including overall occupancy percentage, scheduled check-ins and check-outs for the day, total revenue collected, pending payments, and a status-by-status breakdown of all bookings.
  • The platform provides a centralized audit log viewer that consolidates activity records across user accounts, hotel properties, reservations, payments, and reviews.
  • Administrators can search and filter audit events by service category, event type, date range, or specific user.
  • Each audit entry provides a clear explanation of what occurred, who performed the action, when it took place, and detailed snapshots of data before and after the change.
  • Audit records are strictly permanent and tamper-resistant; they cannot be edited or deleted by any user.

5. Data Persistence Rules

The application shall use four separate MySQL databases — one per microservice — as the permanent storage for all business data: stayease_user_db, stayease_property_db, stayease_reservation_db, and stayease_review_db. No cross-service database joins are permitted; all cross-service data access is performed through REST API calls via WebClient.

  • All successful Create, Update, and Delete operations shall be immediately persisted in the database.
  • All View and Search operations shall always retrieve the latest persisted records from the owning service's database.
  • No business data shall be maintained only in frontend memory; browser localStorage is strictly reserved for the active JWT token (clears on logout or explicit removal).
  • Data shall remain available after browser closure, frontend restart, backend restart, or system reboot. ddl-auto: update ensures schema is kept in sync without data loss on restart; SQL scripts are one-time setup and must not be re-run on an existing database.
  • The database shall always be considered the single source of truth for all business operations.
  • Audit event tables (user_audit_events, property_audit_events, reservation_audit_events, review_audit_events) are append-only; no delete or update operations are permitted on audit records.

9. Non-Functional Requirements

  • Performance: The application should be fast and responsive, with quick load times and minimal lag. All search and availability queries must return results within acceptable time limits even with 18+ hotels and multiple room types.
  • Usability: The application should be easy to use and intuitive, with a clear and consistent UI. Guests should be able to complete a booking within 3 interactions from the hotel search results page.
  • UI/UX Design: Built with Bootstrap 5.3.3 and Bootstrap Icons. Prioritize responsiveness, clarity, and visual consistency across the guest portal and admin portal. Appropriate loading spinners, empty states, and error states must be used throughout.
  • Security: All passwords BCrypt-hashed. JWT stateless authentication enforced on all protected endpoints. Role-based access control strictly enforced — ROLE_USER cannot access admin endpoints and vice versa. Sensitive data (passwords, tokens) must never appear in logs or audit records.
  • Availability / Inventory Integrity: The 10-minute PREPAID inventory hold mechanism must prevent overbooking; the HoldAndExpiryScheduler must reliably expire stale holds even on backend restarts.
  • Fault Tolerance: Resilience4j circuit breakers on all WebClient inter-service calls; appropriate fallback responses must be returned when an upstream service is unavailable, without crashing the calling service.
  • Auditability: Every significant state change in the system must produce an immutable audit event with actor, action, before/after state, and timestamp — across all four services.

10. Implementation Guidelines

10.1 General Coding Practices

  • Use Lombok to generate boilerplate code (e.g., @Data, @Builder, @Slf4j, @RequiredArgsConstructor) for all model and service classes. Prefer constructor injection for dependency management.
  • Implement logic using Java Streams and Lambdas.
  • Organize code into logical layers: controller, service, repository, dto, entity, config, security, client, audit.
  • Use meaningful package names reflecting the domain (e.g., com.stayease.property.service).
  • Use MapStruct for DTO ↔ Entity mapping where applicable; manual mapping may be used in service layers for complex transformations.
  • Employ Spring Dependency Injection for all component management.

10.2 Error Handling

  • Use a centralized @RestControllerAdvice (GlobalExceptionHandler) in each service to intercept, format, and log all exceptions.
  • Implement custom exceptions (e.g., HotelNotFoundException, ReservationConflictException, DuplicateReviewException) with descriptive messages.
  • Return meaningful error responses with appropriate HTTP status codes (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 500 Internal Server Error).
  • Frontend validation errors shall be displayed inline using Bootstrap text-danger spans below the relevant form fields.

10.3 DTOs and Mapping

  • Data Transfer Objects (DTOs) must be used for all API request and response payloads.
  • Database Entities shall never be exposed directly through REST APIs.
  • Separate request DTOs (with Bean Validation annotations) from response DTOs (clean, minimal fields).
  • Sensitive fields (e.g., passwordHash, tokenVersion) must never appear in response DTOs.

10.4 Database Interaction

  • Spring Data JPA Repositories must be used for all database operations.
  • Configure spring.jpa.hibernate.ddl-auto=update for rapid development; SQL scripts are one-time DDL setup.
  • Use @Transactional on all service methods that perform multiple database writes to ensure atomicity.
  • Monetary values (nightly rates, totals) shall use BigDecimal with HALF_UP rounding to 2 decimal places.

10.5 API Design

  • All APIs shall be mapped with an appropriate base URI representing the resource (e.g., /api/properties/hotels, /api/reservations, /api/reviews).
  • Strictly isolate server port numbers: Gateway 8080, User Service 8081, Property Service 8082, Reservation Service 8083, Review Service 8084.
  • Use appropriate HTTP methods (GET, POST, PUT, PATCH, DELETE) with correct Spring-resolved status codes.
